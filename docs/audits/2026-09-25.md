# Workspace health and performance audit — 2026-09-25

The six live workspaces are healthy now, and all six agent transcripts load.
There is substantial avoidable latency in workspace aggregation and the native
Herdr endpoint. The largest confirmed opportunity is to collect editor snapshots
concurrently and keep that work off the endpoint's input/render loop.

Previous work was checkpointed as `fe11d50` (`Recover bridge health without
disrupting live editors`) before this audit. No production code, configuration,
process lifetime, workspace selection, or user input was changed during the audit.

## Scope and evidence

- macOS 27.2, arm64; six editors, eight terminals, six detected agents.
- Live read-only measurements began at 09:33 PDT. Existing clients and agents
  continued running; these are local host timings, not controlled machine-idle
  results or end-to-end iPad/network measurements.
- Inspected bridge/router pings, plugin state, `:messages`, attached UI metadata,
  Moshi workspace/session mappings, transcript WebSocket backlogs, Moshi logs,
  Neovim logs, and process resource use.
- Timed individual RPCs, four concurrent aggregate requests, and serial versus
  concurrent collection of the same six editor snapshots.
- Separately measured the native Herdr endpoint with six disposable minimal

- [Machine-readable measurements](2026-09-25-metrics.json). Raw local evidence and
  probe scripts are under `/private/tmp/neordr-audit-2026-09-25/` and
  `/private/tmp/neordr-{audit,audit-extra,endpoint-perf}.py`; these temporary paths

  `a08286d9cc4a85b12082ba3e69052ddb5527e80af358d020f68c3524bd60f2ad`.

### Where time goes

1. **Process-table enumeration is repeated.**
   [`process::snapshot`](../../src/process.rs) launches `ps -axo` for each process
   snapshot. [`backend::dispatch`](../../src/backend.rs) invokes it for every
   editor session snapshot, pane list, and agent list. Each aggregate therefore
   scans the same host process table at least six times. In comparison, warm Lua
   snapshot construction took only **0.022–0.077 ms median** per editor in-process.
   That microbenchmark excludes RPC, serialization and process classification,
   but clearly rules out Lua layout construction as the main observed cost.

2. **Aggregation is sequential and duplicates validation.**
   [`router::execute`](../../src/router.rs) first enumerates bridges through
   sequential health RPCs, checks selected-editor identity, then retrieves each
   editor snapshot sequentially. All four list methods use full aggregation.
   [`session::bridges`](../../src/session.rs) and
   [`selection::current`](../../src/selection.rs) each perform live checks.

   A read-only probe, with fixed already-validated endpoints, collected the same
   six snapshots in **373.07 ms serially versus 86.14 ms concurrently**, a **4.33×**
   improvement. Parallel health checks took 24.73 ms. This is measured potential,
   not a deployed router speedup: discovery, merging, error policy and generation
   validation still need to be implemented and tested correctly.

3. **The native Herdr endpoint blocks while refreshing its sidebar.**
   [`endpoint::handle`](../../src/endpoint.rs) refreshes the session snapshot
   synchronously on its input/render event loop after 300 ms. The frame interval
   target is 16 ms, but synchronous aggregation can occupy the loop for hundreds
   of milliseconds before it handles another event or emits a frame.

   In the isolated six-editor experiment, 50 lightweight `pane.layout` requests
   through the grouped endpoint had **46.41 ms median, 628.62 ms p95, 662.88 ms max**;
   **13/50 exceeded 100 ms**. The pinned endpoint had **0.45 ms median, 44.60 ms p95,
   48.79 ms max**, with none above 100 ms. This verifies request stalls. We did not
   measure physical input-to-pixel latency. Moshi's Term attachment uses a separate
   PTY/remote-UI path, so these numbers must not be presented as Moshi typing latency.

4. **Socket acceptance adds a small fixed delay.**
   Both [`server`](../../src/server.rs) and [`router`](../../src/router.rs) sleep
   20 ms when nonblocking accept finds no connection. The observed approximately
   9 ms median ping is consistent with that polling delay. An event-driven accept
   loop can remove it, but snapshot aggregation is the larger first target.

5. **Moshi adds additional listing work.**
   Its local workspace endpoint took about 1.7 seconds while a Neordr aggregate
   took about 0.5 seconds. The installed Moshi binary does enrichment and may make
   multiple requests. This audit did not trace the exact per-request breakdown
   inside that binary, so it cannot attribute all remaining time to Neordr or
   predict an exact post-optimization Moshi response time.

## Observability gaps

The current logs cannot prove that no intermittent local failures occurred:

- Detached router standard error goes to `/dev/null`; discovery errors are
  discarded. There is no durable history of recovery attempts or their durations.
- API worker I/O failures are discarded, and there are no per-method latency or
  saturation counters. A healthy ping does not demonstrate a healthy listing path.
- Plugin stderr is retained in memory for its bridge's lifetime and principally
  surfaced on exit. It should be bounded and report recent failures with time and
  recovery status; an old `last_error` or undated `:messages` line is insufficient.
- Agent activity status is always `unknown`; it is not a measured health signal.
- All builds still report version 0.1.0, so health output cannot distinguish the
  installed binary from older resident bridge processes after a live upgrade.

## Recommended implementation order

1. **Add lightweight diagnostics alongside the next performance change.**
   Record method duration, failures, request saturation, last successful editor
   check, bridge recovery events, attached UI identity/dimensions, and build ID.
   Keep a bounded/rotated local log; do not record chat text, input, or credentials.

2. **Collect workspace data concurrently and coalesce overlapping reads.**
   Use bounded parallelism with deterministic result order and a shared collection
   for simultaneous sidebar/list requests. Keep selected-editor generation checks
   and validate mutation targets freshly. Do not cache foreground-process identity
   across chat sends, approvals, or agent launches merely to speed display polling.
   Add scaling cases for 1/6/12 editors, concurrent clients, and one unresponsive
   editor. Choose and document whether partial listings are allowed.

3. **Move native endpoint snapshot collection off the input/render loop.**
   Publish completed snapshots from a worker while continuing to process input and
   redraw. Coalesce refreshes, reject results from obsolete UI epochs/generations,
   and preserve the existing ordered input barriers. Test rapid focus switches,
   workspace close during collection, slow editors, and input routing correctness.
   Use the isolated endpoint experiment as a regression benchmark; a provisional
   target is to eliminate metadata-induced stalls over 100 ms on this fixture.

4. **Share process discovery for display requests; then improve socket polling.**
   Avoid a whole-system subprocess scan per editor per display refresh. A shared
   short-lived process snapshot, or platform-native lookup behind one interface,
   can reduce cost. Index parent relationships instead of repeatedly searching
   the process vector. Preserve fresh process validation for input safety. Replace
   20 ms accept polling with an event-driven wait after the larger costs are fixed.

5. **Make retained remote UIs visible and manageable.**
   Show attachment age, dimensions, and owner, and allow explicit UI-only detach.
   Do not equate an old connection with an abandoned one, and do not close the
   underlying editor. Revisit the 24-hour Mosh network timeout only as a deliberate
   reconnection-policy decision.

No production optimization or cleanup was applied as part of this analysis.

## Follow-up: retained UI and shared Codex daemon

The user confirmed that multiple Moshi clients were intentionally open; the two
narrow `claude-mrbd` UIs above were not evidence of an orphan. A subsequent live
incident in `capela-haskell` did expose one: a 51×43 remote UI remained after its
Mosh transport exited, and its Neordr attachment had been reparented to PID 1.
Stack samples showed the attachment blocked writing input to the inner PTY while
Neovim's remote UI waited to flush output. The attachment could not drain that
output or act on its signal flag. Restarted blocking writes also defeated SIGTERM.

Removing only the verified orphaned UI and attachment restored the editor to
320×71. The editor process and all three terminal jobs retained their identities.
The fix uses nonblocking, cancellable forwarding with output draining during
input backpressure, detects transport-parent exit, and makes teardown writes
best effort. Existing attachments need a reconnect after installing the binary.
This does not expire a still-running Mosh transport solely for network inactivity.

The new lifecycle regression reproduces the deadlock with the previous binary
and passes with the patch. It checks lossless bidirectional transfer, cancellation
with blocked outer output, SIGHUP, SIGTERM, terminal hangup, and parent death.
Real Neovim cases verify size restoration and preservation of editor/terminal jobs.
The complete `scripts/check.sh` suite and a locked release build passed on macOS.

A separate Chat View failure in `neordr` came from Codex 0.157.0's shared managed
daemon. The foreground frontend had no open rollout file, while the daemon's
inherited Herdr identity pointed to another workspace. Correcting Moshi's saved
session mapping alone did not restore discovery. The installed moshi-hook 0.3.26
also accepts a trailing UUID in the terminal title: temporarily exposing the
known thread ID resolved the correct conversation and returned a 103-entry
transcript backlog over WebSocket, without submitting chat input. The temporary
title was restored afterward. Codex's `thread-id` title item was accepted by
`codex doctor`; the supported configuration is documented in the installation
guide. The running frontend still requires restart/resume to load that setting.

After restart, the combined thread title, project name, and UUID exceeded
Codex's terminal-title limit: the live title ended in a truncated UUID followed
by `...`, and Moshi again reported no session ID. Use only `thread-id` in the
title configuration to avoid this truncation. The earlier temporary full-title
probe bypassed Codex's title formatter and did not exercise this limitation.

The user subsequently rejected changing personal agent settings as an integration
requirement. The troubleshooting override was removed from Codex configuration;
the title method above is diagnostic evidence, not the implemented automatic
solution. Inspection after the daemon updated to 0.157.1 still found this thread's
Moshi hook record attributed to another editor and the shared daemon PID. The
frontend's local log records exposed its process identity but no structured
thread ID, and the inspected app-server schemas did not establish a mapping from
another frontend's PID/TTY to its selected thread. Herdr's typed `agent_session`
field can represent the result, but it does not supply the missing association.
An initial `codex resume <id>` argument alone cannot track later in-app conversation
switches. A configuration-free automatic fix remains unimplemented.
